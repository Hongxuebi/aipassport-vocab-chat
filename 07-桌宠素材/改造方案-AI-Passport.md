# 把「大肥鱼桌宠」搬进 AI-Passport（ESP32-C3）· 改造方案

> 目标机：FoloToy **ai-passport**（ESP32-C3，无 PSRAM，8MB Flash，ST7789 240×320，三键）
> 上游：[FoloToy/ai-passport](https://github.com/FoloToy/ai-passport) ｜ 同款硬件已有人跑 DOOM：[YeatsLiao/ai-passport-doom](https://github.com/YeatsLiao/ai-passport-doom)
> 本文数字全部来自本机实跑（ffmpeg 8.1 + PIL 12.1.1），不是估算。

---

## 0. 结论先给

规格定在 **96×96 / 12 fps / 255 色索引 + PackBits**，实测 **56.9 KB/动作**。两档可选：

| 版本 | 动作数 | 帧包 | 用途 |
|---|---|---|---|
| 全量 | 106 | **5.90 MB** | Flash 宽裕（16MB 板 / 关掉 BLE）时用 |
| **精简（推荐）** | **85** | **4.73 MB** | 8MB Flash 默认用这档，砍掉 21 个时令动作 |

> 关键：所有动作共用**一个全局缩放比例**（主体高度中位数 282 px → scale 0.340），所以切换动作时角色大小不会忽大忽小。见 §3.1。

代价是必须放弃 PC 版的四样东西：**透明置顶窗、拖拽甩飞、全屏漫游、WebAudio 合成音效**。它们依赖窗口系统和浏览器 API，C3 上没有任何替代品。其余全部可移植，包括动画链权重、点击回应、25 段"小动作"随机池。

## 1. 目标硬件（决定了方案形态）

| 项目 | 规格 | 对本方案的影响 |
|---|---|---|
| MCU | ESP32-C3，RISC-V 单核 160 MHz | 软件解包够用，但没余量做视频解码 |

| 无触摸屏 | — | **拖拽功能直接作废**，改为"长按换位置" |

## 3. 资源管线（已跑通，脚本在 `_esp32/tools/`）

```
webm(VP9-alpha) ──ffmpeg──▶ RGBA 帧 ──裁切/缩放──▶ 96×96 ──全局 255 色量化──▶
索引帧(0=透明) ──PackBits──▶ 4.5 KB/帧 ──▶ pet_assets.bin
```

### 实测四档（同一批 3 个动作）

| 精灵尺寸 | 帧数/动作 | KB/帧 | KB/动作 | 106 动作合计 | 判定 |
|---|---|---|---|---|---|
| 128×128 | 20 | 8.20 | 166 | 17.6 MB | ❌ 爆 |
| 112×112 | 12 | 6.2 | 75.4 | 7.81 MB | ❌ 太满 |
| 96×96 | 16 | 4.7 | 75.5 | 7.82 MB | ❌ 太满 |
| 96×96（并集裁切） | 12 | 4.53 | 56.6 | 5.27 MB | ⚠️ 角色忽大忽小 |
| **96×96（统一比例）** | **12** | **4.85** | **56.9** | **5.90 MB** | ✅ **定版** |

### 3.1 为什么必须"主体裁切 + 全局统一比例"

第一版按**每段动作自己的并集包围盒撑满画布**，结果是灾难：`放烟花`、`被落叶淹没` 这类幅度大的动作，并集被特效撑到 400×300，角色被缩成一小团；`待机呼吸` 幅度小，角色巨大。**同一只鱼在 106 段里大小乱跳。**

改法两步：

1. **主体包围盒**：逐轴取 **8%~92% 分位**，只裁掉极端飞出去的手臂/特效，而不是按最大那一帧撑。
2. **全局统一比例**：统计全部动作主体高度的中位数（实测 **282 px**），算出 `scale = 96 / 282 = 0.340`，**所有动作都用这个比例**，不按各自 bbox 缩放。

代价：体积从 5.27 → 5.90 MB（+12%，因为角色真的变大了，内容更多），并且幅度极端的那几帧会被裁边。

压缩比 1.91:1（相对原始索引色 96×96=9216 B/帧）。

### 命令

```powershell
# 定版全量打包（106 个动作，约 6~8 分钟）
python H:\AI工具\dafeiyu-pet\_esp32\tools\pack_pet.py `
  --size 96 --fps 12 --max-frames 12 `
  --out H:\AI工具\dafeiyu-pet\_esp32\out_final

# 只抽几个动作快速验证
python ...\pack_pet.py --limit 3 --size 96 --max-frames 12 --out ...\out_test

# 解回来看效果（同时也是 C 解码器的参考实现）
python ...\verify_pet.py ...\out_final\pet_assets.bin --out preview.png
```

### 三个已经踩过的坑（写下来免得重踩）

1. **alpha 全变 255** —— ffmpeg 内置的 `vp9` 解码器**不认** WebM 的 BlockAdditional alpha（`ALPHA_MODE=1`）。必须显式指定 libvpx 并放开实验开关：
   ```
   -c:v libvpx-vp9 -strict experimental -pix_fmt rgba
   ```
   少了 `-strict experimental`，libvpx 会以"Pixel format 'gbrap' is not widely supported"直接拒绝出帧。
2. **每个动作各建一份调色板会跨动作漂色** —— 必须两遍处理：先扫全部动作收集像素样本，建一份**全局 255 色**调色板（索引 0 空出来给透明），第二遍才逐动作量化。
3. **帧间 XOR 差分是负优化** —— 直觉上相邻帧很像应该更好压，实测反而 59.2 > 56.6 KB/动作。原因是桌宠透明区本来就压到极限，XOR 把角色内部变成随机值，PackBits 的游程全被拆散。**不要做**。
4. **每段动作各自撑满画布 → 角色大小乱跳** —— 见 §3.1。必须用主体分位包围盒 + 全局统一 scale 两个一起上，只改一个不够：只改 bbox 仍然会按各自尺寸撑满，只改 scale 又会被极端帧的并集把角色挤小。

## 4. Flash 与 RAM 预算

### Flash（8 MB）

现版 `partitions.csv` 把 7.94 MB 全给了 app，没有余量装资源。改成分区：

```csv
# Name,   Type, SubType, Offset,   Size,     Flags
nvs,      data, nvs,     0x9000,   0x6000,
phy_init, data, phy,     0xf000,   0x1000,
factory,  app,  factory, 0x10000,  0x200000,          # 2 MB 固件
pet,      data, 0x40,    0x210000, 0x5F0000,          # 5.94 MB 帧包
```

| 项 | 大小（精简 85 段） | 说明 |
|---|---|---|
| factory（LVGL + WiFi + BLE + 现有 7 个 demo） | ~1.8–2.4 MB | **最不确定的一项，先 `idf.py size` 量** |
| pet 分区 | **4.73 MB** | 85 个动作，用 `exclude_schedule.txt` 排掉 21 个时令 |
| 合计 | **6.5–7.1 MB** | 8 MB 里还剩 0.9–1.5 MB 余量 ✅ |

**若用全量 106 段**：5.90 MB 资源 + 2 MB 固件 = 7.9 MB，卡在 8 MB 边缘，只剩 ~100 KB。所以 8MB 板**默认走精简版**。

**余量怎么花**（按性价比排序）：
1. **加帧数** 12 → 16（体积 ×1.33 → 6.3 MB）：快动作的抽帧感明显减轻，比放大尺寸划算。
2. 加尺寸 96 → 104（体积 ×1.17 → 5.5 MB）：角色大一圈，但屏占变化不显著。
3. 什么都不加，留余量给将来加表情包 / OTA 双分区。

**砍时令清单**在 `tools/exclude_schedule.txt`（21 条，分类注释齐全），打包时用 `--exclude-file` 引用；想加回哪个就删那一行重跑。**已经执行**，所以上面的预算是按 85 段算的。

### RAM（~400 KB）

| 用途 | 大小 |
|---|---|
| FreeRTOS + 驱动 + LVGL | ~80–150 KB（现有 demo 已占） |
| 双帧缓冲 2 × 96×96×2 | **36.8 KB** |
| 动画任务栈 | 4 KB |
| 解包临时 | 0（边解边写 RGB565，不起中间缓冲） |
| **本方案新增** | **~41 KB** |

C3 上没有 PSRAM，代码里 `heap_caps_malloc(MALLOC_CAP_SPIRAM)` 会失败并回落 `malloc`（已写兼容分支，将来换 S3 可白捡）。

## 8. 验收判据（不接受"我觉得能跑"）

1. `idf.py size` 报的 app 大小 **< factory 分区**，且 `pet_assets.bin` md5 与 PC 侧一致。
2. 首帧上屏 **< 300 ms**（`esp_timer_get_time()` 打点）。
3. 连续播放 30 分钟，`heap_caps_get_free_size(MALLOC_CAP_INTERNAL)` 前后差 **< 4 KB**（无泄漏）。
4. 连续切 20 个动作不黑屏、不花屏（96×96 精灵 + LVGL 局部刷新最容易在边界处翻车）。
5. 12 fps 下 LVGL flush 不丢帧：串口打 `lv_display_get_default()` 的 flush 耗时 p95 < 8 ms。

## 9. 明确说清楚的取舍

- **不是"原样搬过去"**：这是**重做一版**，共享的是素材和动效设计，不是代码。JS（~2800 行）到 C 大约 500 行。
- **96×96 是妥协值**：在 240×320 屏上角色约 96 px 高、占屏高 30%。想更大就得砍动作数——这是 Flash 决定的，不是可以"优化"掉的。
- **12 fps 会让快动作发顿**：原素材 24 fps。12 帧/动作已经能看出"抽帧感"，尤其是小提琴、跳舞这类。如果不在乎 Flash，优先把帧数从 12 提到 16，而不是把尺寸提上去。
- **透明是"填底色"不是真透明**：屏幕上没有 alpha 通道，精灵背景会是一块 96×96 的纯色方块。想不露块，得让 `PET_BG_COLOR` 和页面底色严格一致（代码里已经这样做了）。

## 10. 开机画面（boot splash）

素材：`whale-fantasy-intro-8s.mp4`（1664×856 / 8 秒 / 24fps），**只取右侧女孩的脸**。

> **出处**：来自 GitHub `lxj5820/dsh-boot-animation` 的 `assets/videos/3.mp4`（该仓 License 为 `NOASSERTION`，未声明素材许可）。
> 所以**本仓库不随附这一段动画的任何画面**（帧图/预览页/帧包都已移除），只留打包与解码的代码和这段文字；
> 详见 `素材出处.md`。自用设备上烧的帧包不外发；要对外发固件，得先换成本项目自产的画面。

### 10.1 裁切

原片左侧是纯黑 + 一行小字，脸在右边。裁 **`(1180, 211, 1664, 856)` = 484×645**，比例 0.750，正好等于 240:320，缩放不变形。

裁完眼睛完整、脸颊与嘴唇都在、还留着头发的层次。更松会带一堆黑发，更紧会把上眼睑切掉。

### 10.2 为什么是 120×160 而不是满屏 240×320

| 方案 | 单帧压缩后 | 48 帧 | C3 上的帧缓冲 | 结论 |
|---|---|---|---|---|
| 240×320 | **60.6 KB** | 2.84 MB | **150 KB** | ❌ 体积炸 + 内存装不下 |
| 180×240 | 36.2 KB | 1.70 MB | 86 KB | ❌ 仍超预算 |
| 160×213 | 29.1 KB | 1.37 MB | 68 KB | ⚠️ 勉强 |
| **120×160** | **17.0 KB** | **459 KB（27 帧）** | **37.5 KB** | ✅ 定版 |

两个原因缺一不可：

1. **Flash**：满屏画面是照片级内容，PackBits 只能压到 1.24:1（60.6 KB/帧），48 帧就 2.84 MB，8MB 板放不下。
2. **RAM**：C3 只有 ~400 KB SRAM 还要养 LVGL。240×320 RGB565 一帧 **150 KB**，整帧进不了内存；120×160 只要 **37.5 KB**，能整帧放下。

显示时做 **2 倍最近邻放大**：每行像素写两遍（横向）+ 同一行连发两次（纵向），用 `esp_lcd_panel_draw_bitmap` 一次发 4 行（1.9 KB），160 组刷完一屏。像素感反而像老 LCD，不难看。

### 10.3 播放参数

- **27 帧 / 4.5 秒 = 6 fps**：从 8 秒源片均匀抽 27 帧，6fps 播完 4.5 秒（相当于把 8 秒内容压到 4.5 秒，快放）。原片是慢速特写（推近 + 眨眼 + 泪光），这个速度看起来更有节奏感，开机也不必让人干等。
- 实测解码 + 放大 + 刷屏约 **40 ms/帧**，167 ms 的预算里有大量余量。

### 10.4 分区与烧录

```csv
factory,  app,  factory, 0x10000,  0x200000,     # 2 MB 固件
pet,      data, 0x40,    0x210000, 0x4C0000,     # 4.75 MB 桌宠 85 段
boot,     data, 0x41,    0x6D0000, 0x0E0000,     # 875 KB 开机画面
```

| 项 | 大小 |
|---|---|
| 固件 | ~2 MB |
| 桌宠 85 段 | 4.73 MB |
| 开机画面 27 帧 | 459 KB |
| **合计** | **7.17 MB / 8 MB**（余 830 KB） |

```bash
esptool.py --chip esp32c3 -p COM4 write_flash 0x210000 pet_assets.bin
esptool.py --chip esp32c3 -p COM4 write_flash 0x6D0000 boot_assets.bin
```

调用位置：`app_main()` 里 `bsp_display_init()` 成功之后、`bsp_lvgl_init()` 之前，跑一次 `boot_splash_play()`。拿不到 boot 分区时它只打一条警告并返回，不阻塞开机。

> 帧包格式和桌宠**完全一样**（PET1），所以 `pet_anim_decode()` 一行都不用改 —— 开机画面只是"一个 sprite 是 120×160、动作名叫 `boot` 的帧包"。
